# kb-outofbox: ЧТО мешает нативному scroll-restore iOS на нашей странице

Дата: 2026-09-30 12:38–13:15 GMT+3 · Исполнитель: subagent (frontend-developer) · База: v160w6c6 (локальные копии, БЕЗ деплоя)
Скрипты: `/tmp/kb_oob_sim.py` (варианты a–f), копии кода `/tmp/kb_oob/pwa{,_b,_c,_d,_e,_f}`.
JSON: `/tmp/kb_oob_results.json`. Скриншоты: `/tmp/kb_oob_{a..f}_*.png` (37 шт).
Симуляция: Playwright WebKit, iOS-эмуляция 393×852 DPR3 touch, real-iOS-модель (innerH 852 константа, ступени @50мс, scrollY≠0, stale pageTop, 6 циклов), покадровый джерк-детектор (>2px между ступенями анимации закрытия).

## TL;DR — ГЛАВНЫЙ ОТВЕТ

**На реальном iPhone нативному scroll-restore мешают ТРИ источника scroll-правды, которые в симуляции невидимы (no-op), а на устройстве активны:**

1. **`reset()` (scrollTo(0,0)) через 3 слушателя** — `window scroll` + `vv scroll` + `onVv` (app.js:4917, 5292, 5034). Он существует РАДИ реального устройства: «iOS ПАНУЕТ layout viewport (scrollY≈347) → сбрасываем scroll ВСЕГДА» (v160x8). В СИМуляции scrollY эмулируется патченным дескриптором — реального скролла нет, `reset()` всегда no-op → **0/6 в сим, а на устройстве каждый нативный pan/restore iOS получает контр-скролл к 0 В СЕРЕДИНЕ анимации = дёрганье**.
2. **Инволюционный scroll-clamp из-за формулы высоты**: при закрытии `--vvh` мгновенно = innerHeight (852) → docH сжимается до 852, а layout viewport в этот момент ещё ПАНУТ (scrollY≈80–347 от typing-фазы). maxScroll = 852−852 = 0 < scrollY → **WebKit ОБЯЗАН клэмпить scrollY к 0 одним кадром = невольный рывок всей страницы**. У Авито docH=2643 константа — scroll-место есть ВСЕГДА, клэмпа не бывает, restore плавный. В симуляции это не покрыто: scrollY там патченный дескриптор, клэмп не происходит.
3. **`scrollBottomUnfocus()` мгновенно в клинике закрытия** (app.js:5245): реальный `ma.scrollTop = ma.scrollHeight` в кадре, когда layout в полёте — соперничает с нативным restore.

Плюс **задержка 450мс** = gapWatchdog [450,900,1500]: на реальном устройстве дыра/дёрг после гонки лечится только на 450мс (forceReflow+nudge+scrollCure на первом звонке).

**Ранжирование вариантов: (f) ≫ (b) > (d) > (c) ≫ (e=мёртв). Лучший — (f): заглушить ВСЕ reset()-источники на 600мс после focusout + убрать мгновенный scrollBottomUnfocus. Это убирает ровно те механизмы, которые no-op в сим и активны на устройстве, не трогая ничего, что работает (формулу высоты, typing-сжатие, in-flow композер).**

Важные наблюдения:

1. **(a)–(d), (f) — ВСЕ 0/6**: симуляция соврала ЧЕТВЁРТЫЙ раз подряд (w6b-sim, w6c-sim, w6c6-sim, теперь эта). **Ни один из вариантов, включая все четыре из задания, не отличим симуляцией. Реальное устройство = единственный честный тест** — подтверждено ещё раз.
2. **(e) УБИТ даже в сим**: 13 видимых рывков в 6/6 циклов, скачки 51–210px между ступенями (`650→780: dTop=210.44`, `600→650: dTop=118.56` и т.д.). Причина: transition на computed height ДОГНАЕТ анимацию клавиатуры асинхронно — WebKit анимирует height через transition на элементе (урок w5j подтверждён: transition на custom property не запускается, на реальном computed — запускается), но он конфликтует со ступенчатым resize iOS: на каждой ступени transition ещё едет к предыдущей цели → скачок. **Вариант (e) отброшен окончательно.**
3. **Покадровая модель закрытия в сим (вариант f, cycle 1)**: композер в сим мгновенно встаёт на 803/844 УЖЕ на ПЕРВОЙ ступени закрытия (520) — `--vvh=852` ставится мгновенно при focusout, layout «щёлкает» сразу. На реальном устройстве в этот момент layout viewport ПАНУТ (scrollY от typing-фазы) → клэмп + гонка с нативным restore — в сим не покрыто.
4. **(d) в сим неотличим от базы**: разделённый rAF×3 micro-скролл вообще не виден в метриках симуляции (headless не красит промежуточные кадры) — проверка гипотезы «0→1→0 в одном кадре не красится» симуляцией НЕВОЗМОЖНА в принципе, только реальное устройство.
5. Джерк-детектор ( ступени @50мс, >2px) — рабочий: поймал все 13 рывков (e). Для (a)–(d),(f) — 0 рывков между ступенями.

## 3. Почему на реальном iPhone w6c6 дал задержку+дёрганье при сим 0/6

Что в реальном iOS НЕ покрыто моделью симуляции:

| Механизм реального iOS | В симуляции | Что делает НАША страница на устройстве |
|---|---|---|
| **Нативный scroll-restore при закрытии** (iOS сам скроллит обратно) | scrollY — патченный дескриптор, реального скролла нет | `reset()` (window scroll + vv scroll + onVv) получает КАЖДОЕ реальное событие scroll от нативного restore → контр-скролл scrollTo(0,0) В СЕРЕДИНЕ анимации = **дёрганье**. В сим reset() — всегда no-op (scrollY уже «0» или патченный) |
| **Пан layout viewport при typing** (scrollY≠0 реально) | эмулируется патчем свойства, клэмп не работает | при закрытии `--vvh=innerHeight` сжимает docH до 852 при пане → **невольный scroll-клэмп одним кадром** = рывок. В сим клэмпа нет (скролл ненастоящий) |
| **keyWindow cycle** (анимация клавиатуры асинхронна, vv.height приходит с задержкой) | vv.height меняется синхронно с dispatchEvent | `unmarkKb` поллинги 100/250/500 читают промежуточный vv → класс слетает с задержкой; шапка появляется рывком. Формула высоты мутирует на каждом vv-событии в клинике |
| **Scroll anchoring** (iOS держит низ на конце ленты) | лента реально не перекрашивается | мгновенный `scrollBottomUnfocus` в клинике рвёт anchoring — на устройстве видим как «подтяжку» |

**Итого провал w6c6**: очистка 1-го кадра убрала ТОЛЬКО явные мутации (scrollCure/forceReflow/nudge/settle), но оставила три источника, которые в сим невидимы: **reset()-контр-скролл** (главный), **мгновенный scrollBottom**, **мгновенный --vvh=innerHeight при пане (клэмп)**. На устройстве они дают «задержка (450мс watchdog до лечения) и дёрганье (контр-скролл + клэмп + шапка)». Симуляция врала потому, что **scrollY в ней — эмулированное свойство, а не реальный скролл**: клэмп и контр-скролл физически не происходят.

**Ответ на главный вопрос «ЧТО мешает нативному scroll-restore»:**
1. `reset()` (scrollTo(0,0)) на трёх слушателях — контр-скролл против нативного restore (в сим no-op, на устройстве активен);
2. мгновенное `--vvh = innerHeight` при закрытии при пане layout viewport = невольный scroll-клэмп (docH сжимается, scrollY≠0 → форс-клэмп к 0 одним кадром);
3. мгновенный `scrollBottomUnfocus()` в клинике.

## 4. Ранжирование вариантов для РЕАЛЬНОГО устройства

### 🥇 1-е место: (f) — заглушить reset() на 600мс после focusout + убрать мгновенный scrollBottomUnfocus

**Почему:**
- Единственный вариант, который убирает ровно РЕАЛЬНО-устройственные механизмы: reset()-контр-скролл (3 источника) и мгновенный scrollBottom. Оба в сим no-op — но именно они дают дёрганье на устройстве.
- 600мс покрывает анимацию закрытия (~250-300мс) + запас: нативный restore и контр-пан iOS проходят БЕЗ нашего вмешательства — это максимально близко к «отсутствию механизма» Авито.
- Не трогает то, что работает: формулу высоты w6c, typing-сжатие (reset в focusin-цепочке остаётся), gapWatchdog-страховку, поллинги.
- Риск: 600мс тишины — если iOS зависнет в stale-состоянии, reset не поможет до 600мс; но gapWatchdog [450,900,1500] (forceReflow+nudge) остаётся страховкой. Двойная защита сохранена.
- Сим: 0/6, 0 джерков.

### 🥈 2-е место: (b) — убрать ТОЛЬКО мгновенный scrollBottomUnfocus из клиники

**Почему (если (f) покажется слишком агрессивным):**
- Минимальный однострочный дифф; убирает реальный `ma.scrollTop = ma.scrollHeight` из кадра клиники (соперник нативного restore).
- Поллинг [600,800,1200,2000] остаётся — страховка «предпоследнего сообщения» (v160w5n) после оседания.
- Сим: 0/6. Но не убирает reset()-контр-скролл — главный suspect остаётся.
- Плюс: scroll anchoring iOS (v160w5o-гипотеза) получит шанс работать.

### 3-е: (d) — micro-скролл разделёнными кадрами (rAF×3)
- Механизм правдоподобен (гипотеза «0→1→0 в одном кадре НЕ красится, а разделённый — красится» — согласуется с уроком v160x18: 80px-скролл лечит, 8px в одном кадре — нет), НО: тот же семейство settle уже proven слабым на устройстве (w6c5 провал), и сим НЕ МОЖЕТ проверить покраску промежуточных кадров в принципе. Слепой кандидат.

### 4-е: (c) — scrollCure СТРОГО после анимации [400]
- 400мс — на границе анимации (iOS ~250-300мс, но с вариациями): на устройстве может снова попасть в хвост анимации = рывок 80px. Повторение сценария w6c4/w6c5 («задержка и дёрганье»). Не рекомендую.

### ✂ (e) — transition height 250ms — МЁРТВ
- 6/6 рывков ДАЖЕ в симуляции (13 джерков, скачки 51-210px). Transition на реальном computed height запускается (урок w5j подтверждён) — но догоняет ступени iOS с отставанием = гарантированные скачки. Отброшен окончательно.

## 5. КОНКРЕТНЫЙ дифф для лучшего варианта (f)

### app.js — 4 правки

**1) `onVv` (~5034): заглушить reset на collapse**
```js
// БЫЛО:
const onVv = () => { setVvh(); reset(); requestAnimationFrame(pinBottom); };
// СТАЛО:
const onVv = () => { setVvh(); if (!window.__murmurQuiet) reset(); requestAnimationFrame(pinBottom); };
// kb-oob(f): reset заглушён на collapse — нативный контр-пан/scroll-restore iOS
// проходит нативно. Это УБИРАЕТ контр-скролл против restore = главный
// источник дёрганья на реальном устройстве (в сим no-op → 0/6 всегда,
// симуляция этот механизм НЕ видит).
```

**2) `vv scroll` listener (~5292): заглушить reset на collapse**
```js
// БЫЛО:
vv.addEventListener("scroll", () => { setVvh(); reset(); });
// СТАЛО:
vv.addEventListener("scroll", () => { setVvh(); if (!window.__murmurQuiet) reset(); });
```

**3) `window scroll` listener (~5295): заглушить reset на collapse**
```js
// БЫЛО:
window.addEventListener("scroll", reset, { passive: true });
// СТАЛО:
window.addEventListener("scroll", (e) => { if (!window.__murmurQuiet) reset(); }, { passive: true });
```

**4) focusout (~5196): окно тишины + убрать мгновенный scrollBottomUnfocus**
```js
// БЫЛО:
collapseLockUntil = Date.now() + 500;
// СТАЛО:
collapseLockUntil = Date.now() + 500;
window.__murmurQuiet = true; // kb-oob(f): 600мс тишины для reset() — покрывает
                             // анимацию закрытия (~250-300мс) + запас. Нативный
                             // scroll-restore iOS проходит без контр-скролла.
setTimeout(() => { window.__murmurQuiet = false; }, 600);
```
и
```js
// БЫЛО:
scrollBottomUnfocus();
[600, 800, 1200, 2000].forEach(t => setTimeout(scrollBottomUnfocus, t));
// СТАЛО:
// kb-oob(f)+(b): мгновенный scrollBottomUnfocus УБРАН из клиники закрытия —
// реальный ma.scrollTop в кадре, когда layout в полёте, рвёт нативный
// scroll anchoring/restore. Поллинг 600+ остаётся (страховка после оседания).
[600, 800, 1200, 2000].forEach(t => setTimeout(scrollBottomUnfocus, t));
```

### Что НЕ трогать
- Формулу высоты w6c (`animateVvh(innerHeight)` при focusout) — подтверждена.
- typing-сжатие (reset в focusin-поллингах [50..800] остаётся — там нативный пан не мешает).
- gapWatchdog [450,900,1500] — страховка bug 254861 (stale paint) на устройстве.
- Поллинги setVvh+syncComposerSpace [100..3000] — идемпотентны.

### Ожидаемый эффект на реальном устройстве
- Нативный scroll-restore/counter-pan iOS проходит БЕЗ контр-скролла (600мс тишина) → минус главный дёргающий механизм.
- Мгновенный scrollBottom убран → scroll anchoring iOS работает нативно.
- Формула высоты w6c остаётся мгновенной (клэмп-риск снижается, т.к. reset больше не борется с клэмпом — iOS сам оседает).
- gapWatchdog остаётся страховкой, но на здоровом restore больше не нужен.

**ВАЖНО (честность)**: симуляция дала 0/6 на всех вариантах (4-й раз подряд) — она НЕ доказывает успех (f). Кандидат (f) выбран по РАЗБОРУ КОДА: он убирает ровно те механизмы, которые no-op в сим и активны на устройстве. Финальный вердикт — только реальный iPhone.
