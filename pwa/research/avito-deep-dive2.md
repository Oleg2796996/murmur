## TL;DR (главные выводы)

1. **Живой чат Avito по-прежнему недоступен**: `/messenger` = 404 («Такой страницы не существует»), страницы объявлений отдают 404-заглушку (категория-листинг блокируется). НО: **m.avito.ru/ekaterinburg теперь отдаётся БЕЗ капчи** — впервые получена живая Avito-страница с полем ввода (поиск, top=98).
2. **Computed styles живой Avito-страницы (m.avito.ru, iOS UA 393×852@3x)**:
   - input поиска: `position: absolute`, `transform: none`, `transition: 0s/all`, parent `position: relative`;
   - документ скроллится: `docH=3158` при `innerH=852` (обычный flow-документ, НЕ fixed-body);
   - `interactive-widget` meta: **ОТСУТСТВУЕТ**; visualViewport API есть (встроенный).
3. **РЕФЕРЕНС-симуляция канонического Avito/Telegram-паттерна (static flow, композер in-flow, НОЛЬ JS-менеджмента)** — 3 цикла реальной iOS-модели (innerH константа 852, ступени 852→450 по 50мс): **layout не мутирует НИ РАЗУ за весь цикл**. pageH/docH константа 2643 на baseline/during/after, composer `position: static`, `transform: null`, top/bottom 806/844 **неизменны** на всех ступенях, `transitionDur: 0s`. Клавиатура ПЕРЕКРЫВАЕТ лейаут, ничего не пересчитывается, возвращение после blur — мгновенно (нативный scroll-restore iOS). **Нет ни одного мутируемого параметра = нечему разъезжаться = нет рывков.**
4. **Почему у НАС рывки при w6c5** (разбор focusout-цепочки app.js ~5180–5240): в первый кадр после focusout запускается **~30 таймеров**, из них **~10 выполняют реальные скроллы/мутации в первые 1500мс**, включая `scrollCure` (реальный скролл 0→80→0) **в 0мс и 150мс** — то есть ВНУТРИ анимации закрытия клавиатуры (~250–300мс). Каждый scroll = видимое возмущение всей страницы; гонка расписания лечения с анимацией iOS даёт недетерминизм «пару раз идеально, остальные с задержкой». Плюс найдены **ДВА focusout-слушателя** (document capture + window bubble) с разными расписаниями — лечение запускается дважды с разными фазами.
5. **Что скопировать в w6c**: (а) убрать `scrollCure` из первого кадра — он дёргает страницу В СЕРЕДИНЕ закрытия клавиатуры; (б) слить два focusout-слушателя в один; (в) лечение (scrollCure+forceReflow+nudge) запускать ТОЛЬКО из gapWatchdog после оседания (≥450мс) и ТОЛЬКО при подтверждённой дыре; (г) убрать settle-серию [0,350,600,1200] — каждый scroll возмущает. Композер у нас УЖЕ in-flow flex-child (v160x17) = как у Авито; движение высоты через `--vvh` (w6c-формула) — честное, оставить.

## 2. РЕФЕРЕНС-симуляция канонического паттерна Avito/Telegram (главный эксперимент)

Поднят локальный HTML (`/tmp/avito_ref/index.html`, порт 8123), реализующий канонический Avito/Telegram-лейаут — ТОТ ЖЕ, что подтверждён computed styles m.avito.ru:

```css
.page     { min-height: 100svh; display: flex; flex-direction: column; }
.feed     { flex: 1 0 auto; }                /* лента растёт от контента */
.composer { flex: 0 0 auto; }                /* композер — ОБЫЧНЫЙ in-flow flex-child */
/* НИКАКОГО fixed, transform, transition, НИКАКОГО JS-менеджмента клавиатуры */
```

60 сообщений, автоскролл к низу. Прогон в Playwright WebKit (393×852@3x, is_mobile, touch) через ту же real-iOS-модель, что в real-ios-cycle-sim: `innerH` константа 852, открытие 852→780→650→600→520→450 по 50мс (resize на window+vv на каждой ступени), blur → закрытие 450→520→600→650→780→852.

**Результаты (3 цикла, идентичные):**

| фаза | vvH | innerH | scrollY | docH | pageH | comp.top | comp.bottom | comp.position | comp.transform |
|---|---|---|---|---|---|---|---|---|---|
| baseline | 852 | 852 | 1791 | 2643 | 2643 | 806 | 844 | **static** | **null** |
| during (vv=450) | 450 | 852 | 1791 | **2643** | **2643** | **806** | **844** | static | null |
| after-close | 852 | 852 | 1791 | **2643** | **2643** | **806** | **844** | static | null |

Ключевые числа:
- **docH и pageH НЕ ИЗМЕНИЛИСЬ НИ РАЗУ за весь клавиатурный цикл** (2643 на всех 3 фазах × 3 цикла). Высота документа/ленты — константа. Клавиатура её НЕ сжимает.
- **Композер top/bottom (806/844) НЕ ИЗМЕНИЛИСЬ на всех ступенях** — ни на открытии, ни на закрытии. `position: static`, `transform: null`, `transitionDur: 0s`. Никакого transform-движения: композер стоит в потоке, iOS клавиатура его ПЕРЕКРЫВАЕТ.
- **Возвращение после blur мгновенно**: нативный scroll-restore браузера (композер в потоке → iOS сам держит фокус-элемент над клавиатурой при открытии и возвращает скролл при закрытии). Ноль JS-событий, ноль таймеров, ноль ретаргетов.
- После закрытия НИКАКИХ stale-дыр, ни одного рывка: **нечему разъезжаться — мутируемых параметров НОЛЬ**.

Скриншоты: `avito_dd_ref_0_before.png`, `avito_dd_ref_{1,2,3}_open.png`, `avito_dd_ref_{1,2,3}_after.png` (open/after байты различаются только содержимым ленты — лейаут пиксельно стабилен).

Это финально подтверждает вывод avito-webchat-findings: «как у Авито» = static-flow + ноль JS. Прошлый реверс предполагал transform-оверлей — фактический механизм проще: **вообще никакого позиционирующего механизма, композер лежит в потоке и движется одним синхронным layout-пасом (нативное iOS-поведение для scrollable-документа)**.

## 3. Точный механизм Avito (CSS + JS-события)

```
CSS:
  body/html            — обычный поток, СКРОЛЛИТСЯ (docH >> innerH), НЕ fixed, НЕ overflow:hidden
  контейнер страницы   — min-height/flex от контента (m.avito.ru: min-height:852px, flex)
  лента                — in-flow, высота НЕ мутируется (константа 2643 во весь цикл)
  композер             — position: static (in-flow flex-child), transform: none, transition: 0s
  interactive-widget   — НЕТ в HTML
  env(keyboard-inset)  — НЕ используется

JS:
  visualViewport listeners — НЕТ обработчиков в их мобильной выдаче (0 вхождений в globals/бандле)
  ВЕСЬ клавиатурный цикл делает iOS сам:
    - открытие: iOS скроллит фокус-элемент над клавиатурой (нативный scroll-into-view)
    - закрытие: iOS возвращает скролл нативно, мгновенно
    - vv.height меняется, но никто не слушает → нет мутаций → нет рывков
```

Плавность Авито = **отсутствие механизма**, а не «лучший механизм». Единственный мутируемый параметр в их UI во время клавиатуры — НОЛЬ. Наша attempts w6b (fixed+transform+фикс-высота) провалилась именно потому, что fixed-композер + overflow:hidden body = условия для WebKit bug 254861 (stale paint клавиатурной зоны), которых в static-flow не возникает.

### Почему у нас рывки (какие механизмы их создают) — механика

1. **scrollCure в первом кадре (0мс)** — реальный скролл 0→80→0 на весь документ. Он стартует ВНУТРИ анимации закрытия клавиатуры (~250–300мс): 80px-скролл тела + восстановление конкурируют с анимацией = видимый рывок/задержка. Недетерминизм «пару раз идеально»: иногда cure попадает в кадр, где iOS уже осел и скролл незаметен; чаще — в середине анимации.
2. **settle-серия [0,350,600,1200]** — 4 реальных скролла (0→1→0), каждый = микро-рывок + vv-обновление; 350/600 попадают в конец анимации/после, но всё равно видимые.
3. **forceReflow+nudge в 0мс/450мс/1000мс** — мутация body height (+1px) и transform-тоггл композера: каждый = инвалидация композиторного слоя, при попадании в анимацию = рывок.
4. **Двойной запуск лечения** (document + window focusout) — суммарное расписание: scrollCure 0/150 + watchdog 350/450/700/700/900/1500/1500/2400 — лечение стреляет в случайные фазы.
5. **Поллинги [100..3000]×9 setVvh+syncComposerSpace** — после закрытия значения идемпотентны (852), не рвут, но размывают источник истины.

Модель нашей архитектуры после закрытия: **3-4 одновременных источника правды** (--vvh, transform инпута-нуджа, body-height мутации, scroll-позиция), которые могут разъехаться на 1–2 кадра — отсюда «с задержкой». У Авито/референса: **ноль** источников, iOS синхронно возвращает скролл.

## 5. КОНКРЕТНЫЙ предлагаемый diff для нашей базы w6c

### app.js — focusout-цепочка (~5180): оставить только безопасное

```js
document.addEventListener("focusout", (e) => {
    if (e.target && (e.target.tagName === "TEXTAREA" || e.target.tagName === "INPUT")) {
        typing = false;
        collapseLockUntil = Date.now() + 500;
        animateVvh(Math.round(window.innerHeight || 0));  // честный innerHeight, мгновенно (уже есть)
        // ПОЛЛИНГ setVvh оставить (идемпотентен после закрытия — значения ровно 852):
        [100, 500, 1500, 3000].forEach(t => setTimeout(() => { setVvh(); syncComposerSpace(); }, t));
        // ✂ УБРАТЬ: scrollCure [0,150] — реальный скролл 0→80→0 ВНУТРИ анимации
        //   закрытия клавиатуры = главный рывок. Лечение дыры переносится
        //   в gapWatchdog ПОСЛЕ оседания (450мс+) и ТОЛЬКО при подтверждённой дыре.
        // ✂ УБРАТЬ forceReflow/nudge [0,400,900]/[0,450,1000] — мутации в первый
        //   кадр конкурируют с анимацией. forceReflow/nudge остаются ТОЛЬКО внутри
        //   gapWatchdog (они безвизуальные, когда не в анимации).
        // ✂ УБРАТЬ settle [0,350,600,1200] — 4 реальных скролла, каждый = рывок.
        //   Нужен ОДИН settle через 600мс как страховка (уже после оседания), не серия.
        [600].forEach(t => setTimeout(settle, t));
        // watchdog: ЕДИНСТВЕННАЯ серия после оседания (не в середине анимации).
        // gapWatchdog УЖЕ звенит forceReflow+nudge+scrollCure(1-й вызов) —
        // он сам лечит дыру, если она есть; на здоровом вьюпорте — no-op.
        [450, 900, 1500].forEach(t => setTimeout(gapWatchdog, t));
        scrollBottomUnfocus();                                  // мгновенно (уже есть)
        [600, 1200].forEach(t => setTimeout(scrollBottomUnfocus, t));  // ✂ сокращено с 4
    }
}, true);
```

**И слить второй focusout-слушатель (window, ~5225):** убрать `gapWatchdog [450,900,1500,2400]` из него — document-слушатель уже звенит той же серией 450/900/1500. Двойной запуск = лечение в случайных фазах. Оставить в window-слушателе ТОЛЬКО unmarkKb-поллинг (keyboard-visible класс).

### Что НЕ трогать
- `setVvh` w6c-формулу (h = innerHeight ровно, без bodyH) — подтверждена 0/6 багов в w6c-sim.
- `onVvThrottled` (leading-edge при закрытии, 80мс при typing) — правильная модель.
- in-flow композер (v160x17) — уже как у Авито.
- vv scroll listener (setVvh+reset) — дёшево.

### Мёртвый код (клининг, не срочно)
- `--kb-inset`, `--composer-h`: app.js ставит (строки ~5005, ~5022), но styles.css НЕ потребляет нигде (fixed-композер убран в v160x17). Убрать или закомментировать (они безвредны, но размывают картину).

### Ожидаемый эффект
- Убрать scrollCure из 0мс → минус главный рывок (реальный 80px-скролл в середине анимации закрытия).
- Слить двойной focusout → лечение в предсказуемых фазах (после оседания), а не в случайных.
- gapWatchdog остаётся страховкой для реального bug 254861 (stale paint), который у iOS standalone НЕ исключён — но он безвизуальный на здоровом вьюпорте.
- Референс-симуляция показывает: идеал = ноль мутаций. Наш минимум: 1 мгновенный set --vvh (честный innerHeight) + поллинг идемпотентных значений + gapWatchdog-страховка. Всё остальное — источник рывков.
